# 德州扑克模拟训练器

一个可在手机上运行的德州扑克模拟器，用来反复练习并在每手结束后复盘自己的失误。

核心价值不在「玩牌」，而在**告诉你哪一步打错了、错在哪、亏了多少**，并通过长期统计暴露反复出现的漏洞。

## 当前状态

**引擎、估值、AI 对手、复盘引擎、牌桌与对局会话（③-A）、复盘卡片（③-B）、持久化与历史页（③-C）、漏洞报表与设计稿对齐（③-D-1）已完成。界面是三个页面：牌桌 / 复盘 / 报表。牌桌能完整玩一局：AI 自动行动、hero 下场打牌、手牌结算、破产补码，结算后可打开复盘卡片逐个决策点回看；每手自动落库，历史页可按最大损失/时间排序并按位置·街道·失误分类·是否有异议筛选，支持 JSON 导出导入。**

## 设计要点

**每手牌完全可复现。** 所有随机性来自一个字符串 seed。同样的 seed 和按钮位，牌局逐位相同。出 bug 时贴 seed 就能原样重放。`src/core/` 内禁止调用 `Math.random()`。

**对局与复盘解耦。** 一手牌结束后产出一份自包含的 `HandRecord`（所有底牌、公共牌、完整动作序列、seed）。二期的复盘引擎只吃这份记录，不碰运行中的对局状态——这样复盘规则可以独立测试，改进规则后还能对历史手牌批量重跑。`replayHandRecord()` 已验证记录足以完整复现终局。

**筹码守恒是硬不变量。** `totalChips()` 在一手牌内的任何时刻都必须恒定。这条断言挂在每个动作之后，并由一万手随机自对弈反复冲击。德扑引擎的 bug 有个恶心的特点：**它们不崩溃，只是算错**——边池分错几个 BB、结算多付一次，牌局照常进行，但复盘数据全是脏的。而复盘数据的可信度就是这个项目的全部价值。

**金额比较一律带容差。** 筹码是浮点数，`===` 和裸 `>` 都不安全。`chips.ts` 提供 `isZeroChips` / `chipsGreater` / `round2`，它是个叶子模块（零依赖），保证任何模块都能用而不产生循环依赖。

## 测试策略

正确性主要靠三种手段建立，而不是靠逐个函数写用例：

**对拍。** 牌型评估写了两份实现——一份显然正确的穷举版，一份位运算快速版。10 万组随机 7 张牌，两者结果必须逐位一致。快速版是给蒙特卡洛用的（每个决策点要评估上万手牌），慢版是标尺。

**属性测试。** 一万手随机动作自对弈，断言引擎从不死锁、不重复发牌、不出负筹码、每个动作后筹码守恒。这类测试的价值在于它会走到没人想得到的路径——本项目里边池的一个真 bug 就是 fast-check 的任意生成器撞出来的。

**外部基准。** 蒙特卡洛胜率与精确穷举对拍误差 < 1.5 个百分点，且已知值对得上公开的德扑胜率表（AA 对单个随机手 ≈85%、72o ≈34.5%、AA 对五家 ≈49%）。

### 已知的覆盖边界

- **边池分层自 ③-A 起进入产品路径。** 此前固定 100BB 等额起始筹码使 `buildPots` 每次都合并成单池；③-A 改为筹码跨手延续 + 破产补码（100BB 或 200BB）后，各座位筹码不再恒等，分层真正启用。验收关卡断言 200 手中必须出现多池——若为 0 则停下来查边池，不许换 seed 绕过。
- **`buildPots` 的取整假设输入是分位对齐的。** 引擎产生的投入都经过 `round2`，满足该前提；子分金额（如 0.005）不在支持范围内。
- **盲注不在动作日志里。** `startHand` 直接扣盲，`actions` 开局为空数组。任何靠累加 `Action.amount` 来重建投入的代码，对小盲和大盲都会算错——用 `HandRecord.pots` 或 `replayHandRecord()`。

估值引擎（②-A）这边：

- **EV 是单步近似，不展开未来街的博弈树。** 它能可靠指出明显错误，不该被当作 solver 的精确输出。设计文档 §12 有完整的局限清单。
- **数字带蒙特卡洛噪声。** 默认 2000 次迭代下，一个 150BB 底池上单个 EV 的标准误约 ±1.65 BB，而严重度分级的最小档是 0.2 BB。二期需要把不确定度暴露出来，或按底池大小调整迭代数。
- **隐含赔率只覆盖口袋对。** 同花听牌与开口顺听需要牌面感知的听牌检测，本代码库尚无该能力，留待后续与听牌判定一并实现。在此之前这两类手牌不获得加成——宁可少算。
- **翻前范围表覆盖 24 个节点**（5 个开池 + 15 个面对开池 + 4 个面对 3bet）。未覆盖的节点 `hasNode` 返回 false，由调用方回落到全范围。
- **多人底池按单一跟注者建模。** 弃牌率算的是「所有人都弃牌」，但赔付项按「恰好一人跟注」定价。多人局的数字精度低于单挑。
- **范围塌缩时估值会降级，且会说出来。** 多个对手的范围被收窄到同一小撮组合时，牌堆凑不出互不冲突的发牌。此时引擎按「最窄的先放宽」逐个替换，并在 `EvResult.degraded` 上打标记——复盘引擎必须据此拒绝引用这类数字，否则会拿一个建立在替换范围上的「你亏了 X BB」去告诉用户。

AI 层（②-B-1）这边：

- **性格只影响偏好，不改估值。** `estimateEv` 的输出对所有性格是同一个客观数字，性格作为一个偏好分叠在上面。这保证了 AI 与复盘引擎共享同一套世界观。
- **AI 每次决策约 25ms（最差 33ms）**，6 人桌翻前，100ms 手机预算下有约三倍余量。②-A 收尾时这个数字是 570ms，两个杠杆把它压了下来：翻前牌力改为进程内查表（141 倍），以及把范围放宽从「预先判断可行性」改成「采样真失败才做」。
- **六种性格在开池宽度上确实不同**：岩石 6.97%、紧凶 10.77%、GTO 12.67%、松凶 18.37%、跟注站 20.27%、疯子 24.07%（UTG 位）。放宽用的是并集扩展而非按牌力切前 N%——后者会悄悄删掉 `A5s` 这类为可玩性而非纯胜率入选的开池牌。
- **两百手自对弈是验收关卡**，断言筹码守恒、无死锁、无重复牌、同种子完全可复现。它曾经是空的：`betSize` 对 `call`/`allin` 传了 0，导致尺寸相关的收窄整个失效，自对弈从未产生过塌缩范围——而塌缩正是那一族缺陷的全部内容。修复后最窄范围从 3.17% 降到 0.0726%。**绿色测试套件的说服力取决于它走到了哪些路径，不是它有多少条。**

复盘引擎（②-B-2）这边：

- **复盘不得使用对手的实际底牌。** 用对手最后亮出什么来评判你当时的决策就是结果论——你下注时并不知道。底牌在 `HandRecord` 里唾手可得，所以这条红线由两道测试守着：源码静态扫描，加一个把六个座位的 `holeCards` 全部设成陷阱的 `Proxy` 测试。
- **估值降级时不报数字。** 多个对手范围塌缩到物理上无法同时成立时，引擎会替换范围重算并置 `EvResult.degraded`。此时 `evLoss`/`severity`/`tag`/`actualEv`/`recommended` 全部置空，文案固定为「不做判定」。宁可少说，不可错报。
- **翻前用频率表判「是不是失误」，用 EV 算「亏了多少」。** 均衡策略是混合的，低频但合法的选择不算错（阈值 0.15）。范围表只有频率没有 EV，所以量纲统一靠 EV——翻前与翻后的损失可以直接相加。
- **金标准场景是唯一的正确性锚点。** 其余 500 多个测试证明代码符合设计，只有这 29 个场景证明设计给出的扑克答案是对的。它们已经抓出四个真缺陷，包括两个在真实牌局中永远触发不了的错误分类。**3 个场景如实跳过**——引擎的判定与扑克常识不符，预期没有被修改去迁就实现。
- **已知会影响数字的三处**：EV 引擎的单步近似有时推荐超池全下（spec §12），复盘会原样转述；尚未行动的对手被建模为持有开池范围而非随机牌，hero 胜率因此低估约 4 个百分点；翻前频率短路不看筹码深度，短码本该跟注的弃牌可能被赦免。这三条都要在 UI 上标注，不能让用户把这些数字当作 solver 输出。

牌桌与会话（③-A）这边：

- **对局编排是纯 TS，React 只是壳。** `src/session/` 不得 import React、不得出现计时器与 DOM，`src/ui/` 不得从引擎取值（类型导入除外）。两条由 `src/session/architecture.test.ts` 的结构性守卫盯着。这样做的理由是前三期 534 个测试的说服力全部建立在「纯逻辑、可在 node 里完整驱动」之上，把对局循环写进 React hook 就得把验收关卡搬进 jsdom。
- **会话状态里不存 `Rng`。** 它有内部可变状态，进了 React 状态后 StrictMode 的 effect 双调用会让它多走一步，同 seed 不再复现。改用 `stepIndex` 派生 seed，`stepAi` / `applyHero` 因此是幂等纯函数。**代价：会话层与 `playAiHand` 用的是不同的随机流，同一个 seed 在两者下产生的牌局不相同**，两条路径各自内部可复现，互不对表。
- **实额只存在于 `src/ui/format.ts`。** 界面显示 20/40 盲注、4000 后手，内部量纲仍是 0.5/1 BB 与 100BB——20/40/4000 在 BB 量纲上与原设计完全一致，所以这是显示单位而非引擎改动。EV 损失例外，保持 BB。
- **净盈亏按「当前筹码 − 累计买入」算，不累加每手 `netBB`。** 补码是往桌上添钱不是盈利；账本记的是实际添入额（目标额 − 补码前筹码）而非目标额，否则恒等式会差掉零头。验收关卡用两条独立路径算同一个数来守这条。界面上补码按钮文案「补 4,000」「补 8,000」显示的是补码后的**目标筹码额**（100BB / 200BB），不是本次添加的筹码量——只有补码前筹码恰为 0 时两者才相等。例如破产到 0 后点「补 4,000」，账本只记入 4,000，累计买入由 4,000 增至 8,000，净盈亏仍保持 −4,000 不变。
- **深筹码只标记不修正。** 翻前范围表与 EV 引擎按 100BB 标定，筹码延续后深度会漂移。任一座位开局 ≥ 150BB 即打标记，`isDeepStackHand` 产出、③-B 的复盘卡片消费。本代码库没有深筹码范围表，标记是诚实的下限而不是解决方案。
- **渲染层没有自动化测试。** 只有 `actionBarModel`、`format`（筹码面额拆分、牌面点数拆分）与 `sound` 的 `soundFor`（动作→音效映射）这几层纯逻辑被测到，组件树（含 `App.tsx` 里实际播放音效、读写 `localStorage` 静音状态的接线）靠人工清单验证。这是为避免引入 jsdom 与脆弱组件测试的刻意取舍，代价是渲染回归只能靠人发现。
- **每手重掷对手性格，但筹码延续。** 等于每手换人却把筹码留在座位上，扑克语义上略显奇怪，也让用户无法建立读牌记忆。取舍换来的是对手多样性。
- **牌面点数 10 在界面上显示为 `10`，`src/core/handClass.ts` 的 `RANK_CHARS` 仍用 `T`。** 后者是引擎的手牌类别记法——范围表、AI 开池范围、翻前频率表与复盘文案输出的 `T9s`/`ATo` 都建立在它上面。两处刻意不统一：改 `RANK_CHARS` 会波及范围表与几百个测试，远超视觉改版的范围。
- **桌面上限宽 1040px 且限高 760px 并居中。** 只限宽不限高的话，`.table` 的 `flex: 1` 会在高视口下把牌桌拉成竖椭圆——这是浏览器验收时实测发现并修掉的；窄屏（手机）时两个上限都够不着，行为与限制前一致。
- **音效是四个真实录音 + 四个实时合成的混合方案。** `chip-light` / `chip-heavy` / `pot-win` / `allin` 用 CC0 公有领域录音（来源与许可逐个记在 `public/sounds/CREDITS.md`；放 `public/` 而非 `src/`，Vite 原样拷贝进 `dist/sounds/`，不进 JS bundle）。`deal-card` / `board-flip` / `fold` / `check` 没有对应文件，在 `src/ui/sound.ts` 里用滤波噪声 + 包络实时合成——CC0 库里搜不到合适的卡牌与敲桌素材，主流免费库下载又需要注册账号。
- **静音状态存 `localStorage`（键 `poker-trainer.muted`），是「无持久化」的一处有意例外。** 那条规则针对的是对局状态（刷新即丢，③-C 解决）；一个每次刷新都要重按的静音键是纯粹的烦扰。读写都包在 `try/catch` 里，隐私模式下退化为本次会话内有效。
- **第一手的发牌音不会响。** 浏览器在用户第一次手势前不允许播放音频，而第一手在页面加载时就开始了。这是自动播放策略的必然结果，没有为它写 workaround。

复盘卡片（③-B）这边：

- **复盘结论只活在本次会话里。** 刷新即丢 —— 持久化与历史页是 ③-C。
- **「我不认同这个判定」没做。** 它的唯一用途是在历史页把有争议的手牌筛出来改进规则，而历史页在 ③-C；现在做只是个点了没有去处的按钮。
- **复盘卡片需要手动打开，不会自动弹。** 控制自动弹出的设置开关在 ③-D，本期若强制每手弹出，用户没有地方能关掉它。结算区按钮上的色点已经把「这手有没有打错」前置了。
- **「无法判定」（降级）那条分支实现完整，但真实对局里几乎见不到。** 它在 `estimateEv` 因对手范围互相冲突而采不出样（`InfeasibleSamplingError`）时触发，而现有性格范围足够宽，这个条件基本不成立：`selfPlayAi.test.ts` 那条仅报告的用例实测 200 手里 `equityVsRanges` 调用 11729 次、触发 **0** 次；另行扫描 180 手 / 278 个决策点同样是 0。这条分支是**防御性**的 —— 一旦将来收窄逻辑变严（③-C 起改性格范围，或新增更强的范围收窄），UI 不会拿降级后的数字去骗用户说「你这步的 EV 是多少」。验收时是临时改 `evEstimate.ts` 强制注入才看到它的。
- **候选动作的名字仍是英文（`check` / `bet 1/3` / `all-in`）。** 卡片其余部分已全中文（本手评级、街名、动作名、失误标签），只剩条形图的行标、「推荐：X」和解释文案末尾的「建议X。」这三处。它们印的都是 `EvCandidate.label`，而这个字段同时是**身份串**——`analyzeHand` 靠它把用户的实际动作匹配到候选（`actualLabel`），`judge.ts` 也按它比对。翻译得在产出侧（`core/evEstimate.ts`）做才能让引擎的解释文案与界面口径一致，只在 UI 层贴一张显示映射会让同一张卡片里出现「弃牌」和「建议fold。」并存。这是一次跨层改动 + 一批快照式断言的重写，留给后续。
- **`HandAnalysis` 不是可序列化的 DTO，③-C 落库前必须先处理。** 两处：`situation.opponents[].range` 是 `ReadonlyMap`，`JSON.stringify` 会把它静默变成 `{}`（不报错，取回时范围为空）；`recommended` 与 `candidates` 里的某一项是**同一个对象引用**（`evEstimate.ts` 直接把选中的候选塞进 `recommended`），序列化会把它拆成两份，`===` 判等在取回后失效。目前 UI 全程拿的是内存里的原对象，所以看不出来。

持久化（③-C）这边：

- **落库的不是 `HandAnalysis` 而是视图类型 `HandView`。** 前者带着对手范围（`ReadonlyMap`，`JSON.stringify` 会静默变空）与一个共享对象引用，序列化不了；更要命的是体积——带上范围表单手约 40 KB，一万手 400 MB，是规格 §9 估值的二十倍。范围不落库既为体积，也因为它没用：界面上没有一处渲染对手范围，而「规则升级后批量重跑分析」的输入是 `HandRecord`，范围本来就是从它重新推出来的。**实测单手 ≈ 4.5 KB（view 2.7 + record 1.9），一万手约 45 MB**，仍是规格估的 15 MB 的三倍，如实记下：它在移动端配额内，不构成阻塞。
- **统计是增量更新的，只挡得住「同一手连着来两次」。** `Stats.lastHandId` 防的是 React StrictMode 下 effect 双跑与写入失败后的重试，挡不住乱序插入。导入正是乱序插入，所以导入之后走的是**整表重算**（`recomputeStats`），不是继续增量。将来若加「批量重跑历史」，也必须走重算这条路。
- **统计的累计净盈亏与顶栏那个不是同一个数。** 前者是每手 `netBB` 求和（BB/100 的口径），后者是账本的「当前筹码 − 累计买入」。正常情况相等，但某一手因存储不可用没落库时会分叉。两个数各有各的权威范围，不要拿一个去校验另一个。
- **多标签页会让聚合统计对不上。** 统计文档在内存里有一份缓存，两个标签页各持一份，后写的覆盖先写的。手牌本身不受影响（按 id 写入）。多标签页不是本项目的目标场景，没为它引 BroadcastChannel；下一次「重新计算统计」能修好。
- **存储不可用时牌局照常，但顶栏会亮「未记录」。** 隐私模式、配额满、存储被禁用都会走到这里。不显式说的话，用户会以为每一手都记着了，等想去翻历史才发现是空的。
- **启动时申请持久化存储，但拿不到也照跑。** 默认的 IndexedDB 是 best-effort，浏览器可以在磁盘紧张时把整份数据丢掉且不通知任何人。`navigator.storage.persist()` 是否批准由浏览器决定（通常看站点参与度）。
- **导出文件不含统计。** 它是派生值，一起写进去就多一份可能与手牌对不上的真相；导入侧统一重算。
- **导入时坏记录跳过而不是整份拒绝**，但跳过的条数一定会告诉用户。为一条坏数据把另外几百手挡在门外，是把最坏的结果强加给最需要这个功能的人；而静默丢数据比拒绝更糟。整份文件层面的问题（不是 JSON、格式标记不对、版本更高）则一律拒绝。
- **导出/导入的入口暂时放在历史页。** 规格 §10.6 把它们归在设置页，那一页是 ③-D，到时候整体搬过去。

漏洞报表与设计稿对齐（③-D-1）这边：

- **摘要与手牌分成两个 store，报表只扫摘要。** `hands` 里一手实测约 4.5 KB（record + view），任意窗口的聚合都扫不动它——「全部」档在万手时要读 45 MB。新增的 `summaries` store 每手约 100–150 字节，万手 1.5 MB，任意窗口现算都便宜。摘要是**派生缓存**，任何时候都能从 `hands` 重建。
- **增量的 `applyHand` 与扫窗口的 `aggregate` 是两条算同一批数的路径**，靠一条属性测试锁住口径：同一批 `StoredHand`，`reduce(applyHand)` 与 `aggregate(map(summaryOf))` 的 `hands`/`netBB`/`byTag`/`byStreet`/`byPosition` 必须逐字段相等。这条闸是③-C 那次「两个净盈亏对不上」的教训换来的。
- **摘要带 `v` 版本号，回填在计数不等或版本过期时触发。** 只比条数不够：将来字段集变了，条数仍然相等，陈旧形状的摘要会被静默沿用，而报表数字会错得没人看得出来。
- **回填只在报表页触发，且只比计数不逐条比 id。** 从不打开报表的用户，摘要 store 会一直是空的——不为一个可能永远不看的页面在每个人的启动路径上加一次全表扫描。`onupgradeneeded` 里仍然不做值迁移（那个事务会阻塞启动）。
- **BB/100 与「每百手 EV 损失」是两张独立的卡。** 前者掺着运气，后者衡量决策质量。一段时间里 BB/100 为正而 EV 损失很大是完全可能的——**赢着钱在漏**，那正是最该被看见的情形。
- **曲线超过 240 点后等距抽样，取累计值本身，不做区间平均。** 平均会把回撤削平，而曲线的用处恰恰是让人看见那些坑。
- **报表页与复盘页不做实额换算，牌桌做。** 牌桌回答「你赢了多少钱」（$4,000），复盘与报表回答「你打得多好」（BB/100、EV 损失）。代价是同一手在结算条显示 `本手 −$882`、在复盘页头显示 `−22.1 BB`，两个数并存。
- **砍掉了设计稿 Progress 屏的 "Win rate vs persona"。** 6-max 一桌坐着五个不同性格，「赢的是谁」没有明确语义；③-A 起每手重掷性格，这个数从一开始就是混的。那块位置改放**分位置盈亏**，行结构与设计稿一致。
- **报表的累计净盈亏与顶栏那个仍是两个数**（③-C 已记的分叉）。某一手因存储不可用没落库时会分岔，两个数各有各的权威范围，不要拿一个去校验另一个。
- **复盘从底部滑出的卡片改成了整页两栏。** 导航三项对应设计稿三屏：牌桌 / 复盘 / 报表。历史列表在设计稿里没有对应屏，改由复盘页右栏的「全部手牌」按钮进入（设计稿那颗 All hands 正是这个入口）。`ReviewSheet.tsx` / `ReviewTimeline.tsx` / `RaiseControl.tsx` 随之删除，不留死代码。
- **左栏一街一项、四街恒显示**，状态取该街最严重的 severity，EV 文案取该街 evLoss 之和；点某街，右栏渲染该街的全部决策点。设计稿左栏是四张固定卡片，而 `HandView.decisions` 是逐决策点的，这个映射是两者之间的那层胶水。
- **动作条改成设计稿的两行常驻**（预设 + 滑块 + 金额框 / 弃牌 + 跟注 + 加注），取消了原来的三态互斥切换。**全下的二次确认没有丢，换了形式**：全下预设只把金额推到最大，真正提交仍要点主按钮——「先选额度再确认」本身就是两步。
- **顶栏右侧设计稿那三个图标按钮（▤ ✎ ···）一个都不渲染，游戏名胶囊也不带 `▾`。** 项目原则是「列一个点了没反应的入口比不列更糟」，而本项目只有一种游戏类型。会话盈亏与静音按设计稿搬到了左侧导航底部。
- **座位胶囊按设计稿重组**（头像方块 + 名字 + 状态点 + 筹码），名字用性格中文名、头像放首字；**位置标记没有丢**——扑克里位置是必要信息，设计稿只标了庄家钮。筹码堆与动作徽章并存：徽章说「上一个动作」，筹码堆说「本街投入」，语义不同。
- **界面文案仍全中文**，没有照搬设计稿的英文。这是 ③-A 复刻这份稿子时就定下的。

### ③-D-1 留下的三条

- **复盘卡片里候选动作的名字仍是英文**（`fold` / `call` / `bet 1/3` / `all-in`，以及解释文案末尾的「建议fold。」）。它同时是**身份串**——`analyzeHand` 靠它把用户动作匹配到候选。翻译必须在产出侧 `core/evEstimate.ts` 做，是一次跨层改动 + 一批断言重写，本期没做。
- **牌局结束时底池显示的是「实际被争夺的额度」，不是投入之和。** 对手全下而无人跟满时，多出的部分结算时原样退回，从未被争夺过——实测一手：投入之和 4,453，真正易手的只有 886。`core/pots.ts` 的 `contestedTotal()` 按德扑的退回规则扣掉最高与次高投入的差额；**牌局进行中仍显示投入之和**，那时下注还可能被跟，提前扣掉会让底池在等待对手行动时诡异缩水。
